# 评估和认证

## OWASP 对 ASVS 认证和信任标志的立场

OWASP 是保持厂商中立的非营利组织，不会认证任何厂商、验证方或软件。任何声称符合 ASVS 的保证、信任标志或认证，都不是 OWASP 官方背书；因此，组织应谨慎看待第三方关于 ASVS 认证的声明。

组织可以提供保证服务，但不得声称获得 OWASP 官方认证。

## 如何验证 ASVS 合规性

ASVS 有意不把如何验证合规性规定到测试指南那样细。不过，仍有一些关键点需要强调。

### 验证报告

传统渗透测试报告通常按“例外”报告问题，只列出失败项。然而，ASVS 认证报告应包含范围、所有已检查要求的摘要、发现例外的要求，以及解决问题的指导。有些要求可能不适用（例如无状态 API 中的会话管理），报告中必须注明这一点。

### 验证范围

开发应用的组织通常不会实现所有要求，因为根据应用功能，有些要求可能无关或重要性较低。验证方应明确验证范围，包括组织尝试达到哪个等级，以及纳入了哪些要求。说明时应从已纳入内容的角度出发，而不是只说明未纳入内容。验证方还应对未实现要求被排除的理由给出意见。

这样，验证报告的使用者才能理解验证背景，并就该应用值得何种程度的信任作出知情判断。

验证组织可以自行选择测试方法，但应在报告中披露这些方法，并且理想情况下应可重复执行。根据应用和要求的不同，可以采用人工渗透测试、源代码分析等不同方法来验证输入验证等方面。

### 验证机制

验证具体 ASVS 要求时，可能需要多种不同技术。除了渗透测试（使用有效凭据以获得完整应用覆盖）之外，验证 ASVS 要求还可能需要访问文档、源代码、配置，以及参与开发流程的人员。验证 L2 和 L3 要求时尤其如此。用详细文档提供充分的发现证据是标准做法，这些证据可以包括工作底稿、截图、脚本和测试日志。仅运行自动化工具而不进行深入测试，不足以支撑认证，因为每条要求都必须经过可验证的测试。

使用自动化来验证 ASVS 要求一直是大家关注的话题。因此，有必要澄清一些与自动化测试和黑盒测试相关的要点。

#### 自动化安全测试工具的作用

当动态和静态应用安全测试工具（DAST 和 SAST）等自动化安全测试工具被正确集成到构建流水线中时，它们可能能够识别一些本不应存在的安全问题。然而，如果缺少谨慎配置和调优，它们无法提供所需覆盖范围，而且噪声过高会妨碍真正安全问题的识别和缓解。

虽然这类工具可能覆盖一些更基础、更直接的技术要求，例如输出编码或净化相关要求，但必须注意，它们完全无法验证许多更复杂的 ASVS 要求，也无法验证许多与业务逻辑和访问控制相关的要求。

对于不那么直接的要求，自动化很可能仍然可以使用，但需要编写面向具体应用的验证。这些验证可能类似组织已经在使用的单元测试和集成测试。因此，也许可以利用现有测试自动化基础设施编写这些 ASVS 专项测试。虽然这样做需要短期投入，但能够持续验证这些 ASVS 要求，将带来显著的长期收益。

总之，可自动化测试并不等同于运行现成工具。

#### 渗透测试的作用

虽然 4.0 版中的 L1 曾针对“黑盒”（无文档、无源码）测试进行了优化，但即便在当时，标准也明确指出这不是有效的保证活动，应主动避免。

在无法访问必要附加信息的情况下进行测试，是一种低效且效果有限的安全验证机制，因为它错过了审查源代码、识别威胁和缺失控制，并在更短时间内进行更深入测试的机会。

强烈建议开展以文档或源代码为基础的（混合）渗透测试，使测试人员能够充分访问应用开发人员和应用文档，而不是采用传统渗透测试方式。要验证许多 ASVS 要求，这几乎一定是必要的。
