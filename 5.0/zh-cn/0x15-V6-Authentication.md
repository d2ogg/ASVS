# V6 认证

## 控制目标

认证是建立或确认个人或设备真实性的过程。它包括验证某个人提出的声明或关于某台设备的声明，确保能够抵抗冒充，并防止密码被恢复或截获。

[NIST SP 800-63](https://pages.nist.gov/800-63-3/) 是一项现代的、基于证据的标准，对全球组织都有价值，尤其适用于美国机构以及与美国机构交互的组织。

虽然本章许多要求基于该标准的第二部分，即 NIST SP 800-63B“数字身份指南 - 认证和生命周期管理”，但本章重点关注常见威胁和经常被利用的认证弱点，并不试图全面覆盖该标准中的每一个点。如果需要完全符合 NIST SP 800-63，请参考 NIST SP 800-63。

此外，NIST SP 800-63 的术语有时不同；为提高清晰度，本章通常使用更容易理解的常用术语。

较高安全等级应用的一个常见特性，是能够根据各种风险因素调整所需的认证强度。该特性在“授权”章节中介绍，因为这些机制也需要纳入授权决策。

## V6.1 认证文档

本节包含应用应维护的认证文档相关要求。这对于实现和评估相关认证控制应如何配置至关重要。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **6.1.1** | 验证应用文档定义了如何使用速率限制、反自动化和自适应响应等控制，防御凭据填充和密码暴力破解等攻击。文档必须明确这些控制如何配置，以及如何防止恶意账号锁定。 | 1 |
| **6.1.2** | 验证已记录一组特定上下文词汇，用于防止这些词被用于密码。该列表可以包括组织名称、产品名称、系统标识符、项目代号、部门或角色名称以及类似内容的各种变体。 | 2 |
| **6.1.3** | 验证如果应用包含多条认证路径，这些路径均已连同必须在各路径中一致执行的安全控制和认证强度一起记录。 | 2 |

## V6.2 密码安全

密码在 NIST SP 800-63 中称为“记忆秘密”，包括密码、口令短语、PIN、解锁图案，以及选择正确的小猫或其他图片元素。它们通常被视为“你知道的东西”，并常被用作单因素认证机制。

因此，本节包含确保密码被安全创建和处理的要求。大多数要求属于 L1，因为它们在该等级最重要。从 L2 开始，需要多因素认证机制，而密码可能只是其中一个因素。

本节要求主要与 [NIST 指南](https://pages.nist.gov/800-63-3/sp800-63b.html)的 [&sect; 5.1.1.2](https://pages.nist.gov/800-63-3/sp800-63b.html#memsecretver) 相关。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **6.2.1** | 验证用户设置的密码长度至少为 8 个字符，但强烈建议最少 15 个字符。 | 1 |
| **6.2.2** | 验证用户可以修改自己的密码。 | 1 |
| **6.2.3** | 验证密码修改功能要求用户提供当前密码和新密码。 | 1 |
| **6.2.4** | 验证在账号注册或密码修改期间提交的密码，会与至少前 3000 个符合应用密码策略（例如最小长度）的常见密码集合进行比对。 | 1 |
| **6.2.5** | 验证可以使用任意组成形式的密码，不通过规则限制允许的字符类型。不得要求必须包含最少数量的大写字母、小写字母、数字或特殊字符。 | 1 |
| **6.2.6** | 验证密码输入字段使用 type=password 来遮蔽输入。应用可以允许用户临时查看完整的已遮蔽密码，或查看最后输入的密码字符。 | 1 |
| **6.2.7** | 验证允许使用“粘贴”功能、浏览器密码辅助功能和外部密码管理器。 | 1 |
| **6.2.8** | 验证应用按从用户处收到的原样验证用户密码，不进行截断或大小写转换等任何修改。 | 1 |
| **6.2.9** | 验证允许至少 64 个字符的密码。 | 2 |
| **6.2.10** | 验证用户密码在被发现已泄露或用户主动轮换之前保持有效。应用不得要求定期轮换凭据。 | 2 |
| **6.2.11** | 验证已记录的特定上下文词汇列表会用于防止创建容易猜测的密码。 | 2 |
| **6.2.12** | 验证在账号注册或密码修改期间提交的密码，会与已泄露密码集合进行比对。 | 2 |

## V6.3 通用认证安全

本节包含认证机制安全的一般要求，并说明不同等级的不同期望。L2 应用必须强制使用多因素认证（MFA）。L3 应用必须使用基于硬件的认证，并在经过证明且可信的执行环境（TEE）中执行。这可以包括绑定设备的通行密钥、强制执行 eIDAS 高保证等级（LoA High）的认证器、具有 NIST 认证器保证等级 3（AAL3）的认证器，或等效机制。

虽然这是对 MFA 较为积极的立场，但提高这一门槛对于保护用户至关重要。任何放宽这些要求的尝试，都应附带清晰计划，说明如何在考虑 NIST 指南和相关研究的前提下缓解认证风险。

请注意，在发布时，NIST SP 800-63 将电子邮件视为[不可接受](https://pages.nist.gov/800-63-FAQ/#q-b11)的认证机制（[归档副本](https://web.archive.org/web/20250330115328/https://pages.nist.gov/800-63-FAQ/#q-b11)）。

本节要求涉及 [NIST 指南](https://pages.nist.gov/800-63-3/sp800-63b.html)中的多个章节，包括：[&sect; 4.2.1](https://pages.nist.gov/800-63-3/sp800-63b.html#421-permitted-authenticator-types)、[&sect; 4.3.1](https://pages.nist.gov/800-63-3/sp800-63b.html#431-permitted-authenticator-types)、[&sect; 5.2.2](https://pages.nist.gov/800-63-3/sp800-63b.html#522-rate-limiting-throttling) 和 [&sect; 6.1.2](https://pages.nist.gov/800-63-3/sp800-63b.html#-612-post-enrollment-binding)。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **6.3.1** | 验证用于防止凭据填充和密码暴力破解等攻击的控制，已按应用安全文档实现。 | 1 |
| **6.3.2** | 验证应用中不存在默认用户账号（例如 "root"、"admin" 或 "sa"），或这些账号已被禁用。 | 1 |
| **6.3.3** | 验证访问应用必须使用多因素认证机制，或多个单因素认证机制的组合。对于 L3，其中一个因素必须是基于硬件的认证机制，能够抵抗网络钓鱼攻击中的泄露和冒充，并通过要求用户发起的动作（例如按下 FIDO 硬件密钥或手机上的按钮）来验证认证意图。放宽本要求中的任何考虑因素，都需要完整记录理由，并配套一整套缓解控制。 | 2 |
| **6.3.4** | 验证如果应用包含多条认证路径，不存在未记录的路径，并且安全控制和认证强度会被一致执行。 | 2 |
| **6.3.5** | 验证用户会收到可疑认证尝试（成功或失败）的通知。这可以包括来自异常位置或客户端的认证尝试、部分成功认证（多个因素中只有一个成功）、长时间不活动后的认证尝试，或多次失败后的成功认证。 | 3 |
| **6.3.6** | 验证电子邮件既不会作为单因素认证机制，也不会作为多因素认证机制使用。 | 3 |
| **6.3.7** | 验证认证详情更新后会通知用户，例如凭据重置，或用户名、电子邮件地址修改。 | 3 |
| **6.3.8** | 验证无法从失败的认证挑战中推断有效用户，例如无法基于错误消息、HTTP 响应码或不同响应时间推断。注册和忘记密码功能也必须具备这种保护。 | 3 |

## V6.4 认证因素生命周期和恢复

认证因素可以包括密码、软令牌、硬件令牌和生物识别设备。安全处理这些机制的生命周期对应用安全至关重要，本节包含相关要求。

本节要求主要与 [NIST 指南](https://pages.nist.gov/800-63-3/sp800-63b.html)的 [&sect; 5.1.1.2](https://pages.nist.gov/800-63-3/sp800-63b.html#memsecretver) 或 [&sect; 6.1.2.3](https://pages.nist.gov/800-63-3/sp800-63b.html#replacement) 相关。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **6.4.1** | 验证系统生成的初始密码或激活码使用安全随机方式生成，符合现有密码策略，并在较短时间后或首次使用后过期。这些初始秘密不得被允许成为长期密码。 | 1 |
| **6.4.2** | 验证不存在密码提示或基于知识的认证（所谓“秘密问题”）。 | 1 |
| **6.4.3** | 验证已实现安全的忘记密码重置流程，且不会绕过任何已启用的多因素认证机制。 | 2 |
| **6.4.4** | 验证如果多因素认证因素丢失，会执行与注册时同等级的身份核验。 | 2 |
| **6.4.5** | 验证对会过期的认证机制，会提前足够时间发送续期说明，以便在旧认证机制过期前完成续期；必要时配置自动提醒。 | 3 |
| **6.4.6** | 验证管理用户可以为用户启动密码重置流程，但这不会允许管理员修改或选择用户密码。这可以防止管理员知道用户密码的情况。 | 3 |

## V6.5 通用多因素认证要求

本节提供适用于多种不同多因素认证方法的一般指导。

这些机制包括：

* 查找秘密
* 基于时间的一次性密码（TOTP）
* 带外机制

查找秘密是预先生成的秘密代码列表，类似交易授权码（TAN）、社交媒体恢复码，或包含一组随机值的网格。这类认证机制被视为“你拥有的东西”，因为这些代码被有意设计为不便记忆，因此需要存储在某处。

基于时间的一次性密码（TOTP）是物理令牌或软令牌，会显示持续变化的伪随机一次性挑战。这类认证机制被视为“你拥有的东西”。多因素 TOTP 类似单因素 TOTP，但需要输入有效 PIN 码、生物识别解锁、USB 插入或 NFC 配对，或某些额外值（例如交易签名计算器）来生成最终的一次性密码（OTP）。

带外机制的细节将在下一节提供。

这些章节中的要求主要与 [NIST 指南](https://pages.nist.gov/800-63-3/sp800-63b.html)的 [&sect; 5.1.2](https://pages.nist.gov/800-63-3/sp800-63b.html#-512-look-up-secrets)、[&sect; 5.1.3](https://pages.nist.gov/800-63-3/sp800-63b.html#-513-out-of-band-devices)、[&sect; 5.1.4.2](https://pages.nist.gov/800-63-3/sp800-63b.html#5142-single-factor-otp-verifiers)、[&sect; 5.1.5.2](https://pages.nist.gov/800-63-3/sp800-63b.html#5152-multi-factor-otp-verifiers)、[&sect; 5.2.1](https://pages.nist.gov/800-63-3/sp800-63b.html#521-physical-authenticators) 和 [&sect; 5.2.3](https://pages.nist.gov/800-63-3/sp800-63b.html#523-use-of-biometrics) 相关。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **6.5.1** | 验证查找秘密、带外认证请求或代码，以及基于时间的一次性密码（TOTP）只能成功使用一次。 | 2 |
| **6.5.2** | 验证当查找秘密存储在应用后端且熵小于 112 位（19 个随机字母数字字符或 34 个随机数字）时，会使用经批准的密码存储哈希算法进行哈希，并加入 32 位随机盐。如果秘密具有 112 位或以上熵，则可以使用标准哈希函数。 | 2 |
| **6.5.3** | 验证查找秘密、带外认证代码和基于时间的一次性密码种子，使用密码学安全伪随机数生成器（CSPRNG）生成，以避免可预测值。 | 2 |
| **6.5.4** | 验证查找秘密和带外认证代码至少具有 20 位熵（通常 4 个随机字母数字字符或 6 个随机数字即可满足）。 | 2 |
| **6.5.5** | 验证带外认证请求、代码或令牌，以及基于时间的一次性密码（TOTP）具有已定义的生命周期。带外请求的最长生命周期必须为 10 分钟；TOTP 的最长生命周期为 30 秒。 | 2 |
| **6.5.6** | 验证任何认证因素（包括物理设备）在被盗或其他丢失情况下都可以撤销。 | 3 |
| **6.5.7** | 验证生物识别认证机制只作为次要因素，与“你拥有的东西”或“你知道的东西”配合使用。 | 3 |
| **6.5.8** | 验证基于时间的一次性密码（TOTP）根据可信服务提供的时间源检查，而不是根据不可信或客户端提供的时间检查。 | 3 |

## V6.6 带外认证机制

这通常涉及认证服务器通过安全的辅助通道与物理设备通信。例如，向移动设备发送推送通知。这类认证机制被视为“你拥有的东西”。

不允许使用电子邮件和 VOIP 等不安全的带外认证机制。PSTN 和 SMS 认证目前被 NIST 视为[“受限”认证机制](https://pages.nist.gov/800-63-FAQ/#q-b01)，应逐步弃用，改用基于时间的一次性密码（TOTP）、密码学机制或类似机制。NIST SP 800-63B [&sect; 5.1.3.3](https://pages.nist.gov/800-63-3/sp800-63b.html#-5133-authentication-using-the-public-switched-telephone-network) 建议，如果绝对必须支持电话或 SMS 带外认证，应处理设备更换、SIM 更换、号码携转或其他异常行为的风险。虽然本 ASVS 小节没有把这作为强制要求，但对于敏感 L2 应用或 L3 应用，如果不采取这些预防措施，应被视为重大风险信号。

请注意，NIST 最近还提供了[不鼓励使用推送通知](https://pages.nist.gov/800-63-4/sp800-63b/authenticators/#fig-3)的指导。虽然本 ASVS 小节没有这样规定，但了解“推送轰炸”风险很重要。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **6.6.1** | 验证使用公共交换电话网络（PSTN）通过电话或 SMS 发送一次性密码（OTP）的认证机制，只有在电话号码已预先验证、同时提供更强替代方法（例如基于时间的一次性密码），并且服务向用户提供其安全风险信息时才可提供。对于 L3 应用，不得提供电话和 SMS 作为选项。 | 2 |
| **6.6.2** | 验证带外认证请求、代码或令牌绑定到生成它们的原始认证请求，且不能用于之前或之后的请求。 | 2 |
| **6.6.3** | 验证基于代码的带外认证机制通过速率限制防范暴力破解攻击。也可考虑使用至少 64 位熵的代码。 | 2 |
| **6.6.4** | 验证在使用推送通知进行多因素认证时，会使用速率限制防止推送轰炸攻击。数字匹配也可缓解这种风险。 | 3 |

## V6.7 密码学认证机制

密码学认证机制包括智能卡或 FIDO 密钥，用户需要将密码学设备插入或配对到计算机才能完成认证。认证服务器会向密码学设备或软件发送挑战 nonce，设备或软件再基于安全存储的密码学密钥计算响应。本节要求为这些机制提供实现层面的指导，而密码学算法方面的指导位于“密码学”章节。

如果密码学认证使用共享密钥或秘密密钥，这些密钥应使用与其他系统秘密相同的机制进行存储，具体见“配置”章节中的“秘密管理”小节。

本节要求主要与 [NIST 指南](https://pages.nist.gov/800-63-3/sp800-63b.html)的 [&sect; 5.1.7.2](https://pages.nist.gov/800-63-3/sp800-63b.html#sfcdv) 相关。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **6.7.1** | 验证用于核验密码学认证断言的证书以防篡改的方式存储。 | 3 |
| **6.7.2** | 验证挑战 nonce 长度至少为 64 位，并且在统计意义上唯一，或在密码学设备生命周期内唯一。 | 3 |

## V6.8 使用身份提供方进行认证

身份提供方（IdP）为用户提供联合身份。用户通常会在多个 IdP 中拥有多个身份，例如使用 Azure AD、Okta、Ping Identity 或 Google 的企业身份，或使用 Facebook、Twitter、Google、WeChat 等个人身份。这些只是常见选择，并不代表对这些公司或服务的认可，而是提醒开发人员考虑一个现实：许多用户已经拥有多个既有身份。组织应根据 IdP 身份核验强度的风险评估，考虑是否与现有用户身份集成。例如，政府组织不太可能接受社交媒体身份作为敏感系统的登录方式，因为这类身份很容易伪造或仅供一次性使用；而移动游戏公司则很可能需要与主要社交媒体平台集成，以扩大活跃玩家群体。

安全使用外部身份提供方需要谨慎配置和验证，以防止身份冒充或伪造断言。本节提供处理这些风险的要求。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **6.8.1** | 验证如果应用支持多个身份提供方（IdP），用户身份不能通过另一个受支持的身份提供方被冒充（例如使用相同用户标识符）。标准缓解方式是应用使用 IdP ID（作为命名空间）和用户在该 IdP 中的 ID 组合来注册和识别用户。 | 2 |
| **6.8.2** | 验证始终检查认证断言（例如 JWT 或 SAML 断言）是否带有数字签名，以及签名是否完整有效，并拒绝任何未签名或签名无效的断言。 | 2 |
| **6.8.3** | 验证 SAML 断言在有效期内只会被唯一处理并使用一次，以防止重放攻击。 | 2 |
| **6.8.4** | 验证如果应用使用独立身份提供方（IdP），并且对特定功能期望特定认证强度、方法或新近程度，应用会使用 IdP 返回的信息进行验证。例如，如果使用 OIDC，可以通过验证 ID Token 声明（如存在）中的 'acr'、'amr' 和 'auth_time' 来实现。如果 IdP 不提供这些信息，应用必须有已记录的回退方案，并假定使用的是最低强度认证机制（例如使用用户名和密码的单因素认证）。 | 2 |
