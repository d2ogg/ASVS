# V9 自包含令牌

## 控制目标

自包含令牌的概念最早见于 2012 年发布的 OAuth 2.0 规范 RFC 6749。这类令牌自身携带数据或声明，接收方会直接依据其中的信息作出安全决策。另一类简单令牌只包含一个标识符，接收方需要用它在本地查询实际数据，两者不能混淆。常见的自包含令牌包括 JSON Web Token（JWT）和 SAML 断言。

如今，自包含令牌早已不限于 OAuth 和 OIDC。要安全使用这类令牌，不仅要确认令牌没有遭到篡改，还要确认它适用于当前服务和当前用途。这些检查很容易出错，本章将说明应用必须采取哪些措施。

## V9.1 令牌来源和完整性

本节包含若干要求，用于确保令牌由可信方生成且未被篡改。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **9.1.1** | 验证应用在信任自包含令牌中的任何内容之前，先使用数字签名或消息认证码（MAC）确认令牌没有遭到篡改。 | 1 |
| **9.1.2** | 验证创建和校验自包含令牌时，只能使用当前场景允许的算法。算法允许列表中不得包含 `None`；最好只允许对称算法或非对称算法中的一类。如果必须同时支持两类算法，则需要采取额外措施防止密钥混淆。 | 1 |
| **9.1.3** | 验证校验自包含令牌所用的密钥材料来自预先配置的可信来源，并且该来源属于令牌签发方，不能由攻击者自行指定。对于 JWT 及其他 JWS 结构，必须对照可信来源允许列表检查 `jku`、`x5u`、`jwk` 等头字段。 | 1 |

## V9.2 令牌内容

根据自包含令牌作出安全决策前，必须确认令牌仍在有效期内，而且确实签发给当前服务、用于当前用途。这样可以避免某个服务误用签发给另一个服务的令牌，也可以避免混用同一签发方签发的不同类型令牌。

OAuth 和 OIDC 的具体要求在专门章节中覆盖。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **9.2.1** | 验证令牌包含有效时间范围时，应用只在当前校验时间位于该范围内时接受令牌及其内容。对于 JWT，必须检查 `nbf` 和 `exp` 声明。 | 1 |
| **9.2.2** | 验证接收方在信任令牌内容之前，会确认令牌类型正确且符合当前用途。例如，只有访问令牌可以用于授权决策，只有 ID Token 可以用于证明用户已经完成认证。 | 2 |
| **9.2.3** | 验证服务只接受以自身为预期受众的令牌。对于 JWT，可以对照服务配置的受众允许列表检查 `aud` 声明。 | 2 |
| **9.2.4** | 验证签发方使用同一私钥为不同受众签发令牌时，每个令牌都包含能够唯一标识预期受众的限制，防止令牌被其他受众误用。受众标识符由外部动态配置时，签发方还必须验证该标识符，防止攻击者冒充其他受众。 | 2 |
