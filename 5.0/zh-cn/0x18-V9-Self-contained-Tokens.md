# V9 自包含令牌

## 控制目标

自包含令牌的概念在 2012 年的原始 RFC 6749 OAuth 2.0 中已有提及。它指包含数据或声明的令牌，接收服务会依赖这些数据或声明作出安全决策。它应与只包含一个标识符的简单令牌区分开来，后者由接收服务用于在本地查找数据。自包含令牌最常见的例子是 JSON Web Token（JWT）和 SAML 断言。

自包含令牌的使用已经非常广泛，甚至超出了 OAuth 和 OIDC 的范围。同时，这种机制的安全性取决于能否验证令牌的完整性，并确保令牌在特定上下文中有效。这个过程容易出现许多问题，本章详细说明应用应具备的机制，以避免这些问题。

## V9.1 令牌来源和完整性

本节包含若干要求，用于确保令牌由可信方生成且未被篡改。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **9.1.1** | 验证在接受自包含令牌内容之前，会使用其数字签名或 MAC 验证令牌，以防止篡改。 | 1 |
| **9.1.2** | 验证在给定上下文中，只能使用允许列表中的算法创建和验证自包含令牌。允许列表必须包含允许使用的算法，理想情况下只包含对称算法或非对称算法中的一种，并且不得包含 'None' 算法。如果必须同时支持对称和非对称算法，则需要额外控制以防止密钥混淆。 | 1 |
| **9.1.3** | 验证用于验证自包含令牌的密钥材料来自令牌签发方的可信预配置来源，防止攻击者指定不可信来源和密钥。对于 JWT 和其他 JWS 结构，必须根据可信来源允许列表验证 'jku'、'x5u' 和 'jwk' 等头字段。 | 1 |

## V9.2 令牌内容

在基于自包含令牌内容作出安全决策之前，必须验证该令牌是在有效期内提交的，并且它是为接收服务以及当前提交目的而设计的。这有助于避免不同服务之间，或同一签发方的不同令牌类型之间发生不安全的交叉使用。

OAuth 和 OIDC 的具体要求在专门章节中覆盖。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **9.2.1** | 验证如果令牌数据中存在有效时间范围，则只有在验证时间位于该有效时间范围内时，才接受令牌及其内容。例如，对于 JWT，必须验证 'nbf' 和 'exp' 声明。 | 1 |
| **9.2.2** | 验证接收令牌的服务在接受令牌内容之前，会验证该令牌类型正确，并且适用于预期目的。例如，只有访问令牌可以用于授权决策，只有 ID Token 可以用于证明用户认证。 | 2 |
| **9.2.3** | 验证服务只接受预期用于该服务的令牌（受众）。对于 JWT，可以通过根据服务中定义的允许列表验证 'aud' 声明来实现。 | 2 |
| **9.2.4** | 验证如果令牌签发方使用同一个私钥为不同受众签发令牌，则已签发令牌包含能够唯一标识预期受众的受众限制。这可以防止令牌被意外受众重复使用。如果受众标识符是动态配置的，令牌签发方必须验证这些受众，确保不会导致受众冒充。 | 2 |
