# V11 密码学

## 控制目标

本章给出使用密码学时普遍适用的最佳实践，帮助读者理解基本原则，并推动应用采用更现代、更能适应未来变化的方案。主要目标包括：

* 实现稳健的密码学系统，使其能够安全地处理故障、适应不断演化的威胁，并具备面向未来的能力。
* 使用既安全又符合行业最佳实践的密码学机制。
* 维护安全的密码学密钥管理系统，并配备适当的访问控制和审计。
* 定期评估密码学环境，识别新风险，并相应调整算法。
* 在应用生命周期内发现和管理密码学用例，确保所有密码学资产都被纳入清单并受到保护。

除了一般原则和最佳实践，附录 C“密码学标准”还提供了更深入的技术说明，包括本章所称“已批准”的算法和工作模式。

秘密管理、通信安全等具体场景中的密码学要求，分别列在本标准的其他章节。

## V11.1 密码学资产清单和文档

应用需要建立稳健的密码学架构，根据数据的分类采取相应保护。所有内容一律加密会浪费资源；完全不加密又可能违反法律义务。二者之间的取舍应在架构设计、高层设计、设计冲刺或架构探索阶段完成。等到开发后期再临时拼凑或补救密码学方案，成本通常远高于从一开始就做好设计。

定期发现、清点和评估所有密码学资产至关重要。具体方法请参见附录。

让密码学系统能够抵御未来量子计算发展带来的影响也至关重要。后量子密码学（PQC）指为抵御量子计算机攻击而设计的密码学算法；量子计算机预计能够破解 RSA 和椭圆曲线密码学（ECC）等广泛使用的算法。

关于经过审查的 PQC 原语和标准的当前指导，请参见附录。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **11.1.1** | 验证应用制定了书面的密码学密钥管理策略，并按照 NIST SP 800-57 等标准管理密钥的整个生命周期。策略必须防止密钥被过度共享；例如，共享秘密最多只供两个实体使用，私钥只能由一个实体持有。 | 2 |
| **11.1.2** | 验证应用建立并持续更新密码学资产清单，其中列出所有密码学密钥、算法和证书。清单还必须说明每个密钥可以和不可以在系统的哪些位置使用，以及可以和不可以保护哪些类型的数据。 | 2 |
| **11.1.3** | 验证应用使用密码学发现工具或机制，找出系统中的所有密码学操作，包括加密、哈希和数字签名。 | 3 |
| **11.1.4** | 验证应用持续维护密码学资产清单，并在其中记录迁移到新密码学标准（例如后量子密码学）的计划和路径，以应对未来威胁。 | 3 |

## V11.2 安全密码学实现

本节规定如何选择、实现和持续管理应用的核心密码学算法。应用只能采用稳健、得到业界认可的密码学原语，并遵循 NIST、ISO/IEC 等现行标准和最佳实践。选择每个密码学组件时，都必须有同行评审资料和实际安全测试作为依据。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **11.2.1** | 验证所有密码学操作都采用经过业界检验的实现，包括软件库和硬件加速实现。 | 2 |
| **11.2.2** | 验证应用具备密码敏捷性，可以随时重新配置、升级或替换随机数生成方式、认证加密算法、MAC 或哈希算法、密钥长度、迭代轮数、密码套件和工作模式。应用还必须能够更换密钥和密码，并重新加密已有数据。这样，在现有机制失效或获批准的高保证后量子密码学（PQC）实现普及后，应用才能平稳迁移。 | 2 |
| **11.2.3** | 验证所有密码学原语在当前算法、密钥长度和配置下，至少达到 128 位安全强度。例如，256 位 ECC 密钥约等于 128 位安全强度；RSA 则需要 3072 位密钥才能达到同等水平。 | 2 |
| **11.2.4** | 验证所有密码学操作均采用常数时间实现，比较、计算和返回过程中不会因“短路”而提前结束，从而避免通过执行时间泄露信息。 | 3 |
| **11.2.5** | 验证所有密码学模块在发生错误时都能以安全方式终止或降级，而且错误处理不会引入填充预言机（Padding Oracle）等漏洞。 | 3 |

## V11.3 加密算法

采用 AES 或 ChaCha20 的认证加密算法，是现代密码学实践的基础。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **11.3.1** | 验证应用没有使用 ECB 等不安全的分组密码工作模式，也没有使用 PKCS#1 v1.5 等强度不足的填充方案。 | 1 |
| **11.3.2** | 验证应用只使用已批准的密码学算法和工作模式，例如 AES-GCM。 | 1 |
| **11.3.3** | 验证加密数据同时受到完整性保护，攻击者无法在未获授权的情况下修改数据。应优先采用已批准的认证加密算法；也可以把已批准的加密算法与已批准的 MAC 算法组合使用。 | 2 |
| **11.3.4** | 验证同一个 nonce、初始化向量或其他一次性数值不会在不同的“加密密钥与数据”组合中重复使用。生成这些数值的方法必须符合所用算法的要求。 | 3 |
| **11.3.5** | 验证加密算法与 MAC 算法组合使用时，始终采用“先加密、后计算 MAC”（Encrypt-then-MAC）的顺序。 | 3 |

## V11.4 哈希和基于哈希的函数

密码学哈希用于多种密码学协议，例如数字签名、HMAC、密钥派生函数（KDF）、随机位生成和密码存储。密码学系统的安全性取决于其底层哈希函数的强度。本节概述在密码学操作中使用安全哈希函数的要求。

关于密码存储和附录中的相关密码学内容，还可以参考 [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#password-hashing-algorithms)。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **11.4.1** | 验证数字签名、HMAC、KDF、随机位生成等通用密码学用途只采用已批准的哈希函数。MD5 等被禁止的哈希函数不得用于任何密码学目的。 | 1 |
| **11.4.2** | 验证密码使用已批准且计算成本足够高的密钥派生函数（也称“密码哈希函数”）进行存储，并按照最新指导配置参数。参数需要兼顾安全性和性能，使暴力破解在目标安全等级下足够困难。 | 2 |
| **11.4.3** | 验证数字签名、数据认证或完整性保护所使用的哈希函数具有所需的抗碰撞能力和足够的输出长度。需要抗碰撞时，输出长度至少为 256 位；只需抵抗第二原像攻击时，输出长度至少为 128 位。 | 2 |
| **11.4.4** | 验证应用从密码派生秘密密钥时，使用已批准并配置了密钥拉伸参数的密钥派生函数。参数需要兼顾安全性和性能，使暴力破解难以危及派生出的密码学密钥。 | 2 |

## V11.5 随机值

密码学安全伪随机数生成器（CSPRNG）很难自行正确实现。系统中的高质量熵源可能因过度使用而耗尽；随机性不足的来源又会生成可预测的密钥和秘密。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **11.5.1** | 验证所有需要防止猜测的随机数和随机字符串都由密码学安全伪随机数生成器（CSPRNG）生成，并且至少包含 128 位熵。UUID 不满足此要求。 | 2 |
| **11.5.2** | 验证随机数生成机制即使在请求量很高时也能安全、可靠地工作。 | 3 |

## V11.6 公钥密码学

当多个参与方之间无法或不适合共享秘密密钥时，会使用公钥密码学。

作为其中一部分，需要使用已批准的密钥交换机制，例如 Diffie-Hellman 和椭圆曲线 Diffie-Hellman（ECDH），以确保密码学系统能够抵御现代威胁。“安全通信”章节提供了 TLS 要求，因此本节要求适用于除 TLS 之外使用公钥密码学的场景。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **11.6.1** | 验证密钥的生成和播种，以及数字签名的生成和验证，只采用已批准的密码学算法和工作模式。密钥生成算法不得产生容易受到已知攻击的弱密钥，例如容易被 Fermat 分解法破解的 RSA 密钥。 | 2 |
| **11.6.2** | 验证 Diffie-Hellman 等密钥交换使用已批准的密码学算法和安全参数，防止攻击者破坏密钥建立过程，进而实施中间人攻击或攻破密码学保护。 | 3 |

## V11.7 使用中数据的密码保护

必须保护正在处理中的数据。可以采用全内存加密、传输加密等技术，并在数据使用完毕后尽快重新加密。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **11.7.1** | 验证应用采用全内存加密，在敏感数据处理期间防止未经授权的用户或进程访问这些数据。 | 3 |
| **11.7.2** | 验证应用遵循数据最小化原则，把处理过程中暴露的数据降到最低，并在使用完毕后立即或尽快重新加密。 | 3 |
