# V11 密码学

## 控制目标

本章目标是定义密码学通用使用的最佳实践，同时帮助读者建立对密码学原则的基本理解，并推动转向更具韧性、更现代的方法。它鼓励：

* 实现稳健的密码学系统，使其能够安全地处理故障、适应不断演化的威胁，并具备面向未来的能力。
* 使用既安全又符合行业最佳实践的密码学机制。
* 维护安全的密码学密钥管理系统，并配备适当的访问控制和审计。
* 定期评估密码学环境，识别新风险，并相应调整算法。
* 在应用生命周期内发现和管理密码学用例，确保所有密码学资产都被纳入清单并受到保护。

除概述一般原则和最佳实践外，本文档还在附录 C - 密码学标准中提供了关于本章要求的更深入技术信息。其中包括在本章要求语境下被视为“已批准”的算法和模式。

使用密码学解决其他问题的要求，例如秘密管理或通信安全，会位于标准的其他部分。

## V11.1 密码学资产清单和文档

应用需要具备稳健的密码学架构，以便根据数据资产的分类实施保护。加密一切会造成浪费；什么都不加密则可能在法律上构成疏忽。必须在二者之间取得平衡，这通常应在架构设计、高层设计、设计冲刺或架构探索阶段完成。临时拼凑密码学方案或事后补救，其安全实现成本最终必然远高于从一开始就内建安全。

定期发现、清点和评估所有密码学资产至关重要。具体方法请参见附录。

让密码学系统能够抵御未来量子计算发展带来的影响也至关重要。后量子密码学（PQC）指为抵御量子计算机攻击而设计的密码学算法；量子计算机预计能够破解 RSA 和椭圆曲线密码学（ECC）等广泛使用的算法。

关于经过审查的 PQC 原语和标准的当前指导，请参见附录。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **11.1.1** | 验证已制定成文的密码学密钥管理策略，并按照 NIST SP 800-57 等密钥管理标准管理密码学密钥的生命周期。其中应确保密钥不会被过度共享（例如，共享秘密仅限两个实体使用，私钥仅限一个实体使用）。 | 2 |
| **11.1.2** | 验证已建立、维护并定期更新密码学资产清单，且清单涵盖应用使用的所有密码学密钥、算法和证书。清单还必须记录密钥在系统中允许和禁止使用的位置，以及允许和禁止使用这些密钥保护的数据类型。 | 2 |
| **11.1.3** | 验证使用密码学发现机制识别系统中所有密码学实例，包括加密、哈希和签名操作。 | 3 |
| **11.1.4** | 验证密码学资产清单得到持续维护。该清单必须包含成文的迁移计划，说明如何迁移到新的密码学标准（例如后量子密码学），以应对未来威胁。 | 3 |

## V11.2 安全密码学实现

本节定义应用核心密码学算法的选择、实现和持续管理要求。目标是确保只部署稳健且获行业认可的密码学原语，并与当前标准（例如 NIST、ISO/IEC）和最佳实践保持一致。组织必须确保每个密码学组件的选择都有同行评审证据和实际安全测试作为依据。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **11.2.1** | 验证密码学操作使用经过行业验证的实现（包括库和硬件加速实现）。 | 2 |
| **11.2.2** | 验证应用具备密码敏捷性，使随机数生成、认证加密、MAC 或哈希算法、密钥长度、轮数、密码套件和模式可随时重新配置、升级或替换，以应对密码学机制失效。同样，也必须能够替换密钥和密码并重新加密数据。这样，当获得批准的 PQC 方案或标准的高保证实现得到广泛支持后，就可以平滑升级到后量子密码学（PQC）。 | 2 |
| **11.2.3** | 验证所有密码学原语根据所用算法、密钥长度和配置，至少提供 128 位安全强度。例如，256 位 ECC 密钥大约提供 128 位安全强度，而 RSA 需要 3072 位密钥才能达到 128 位安全强度。 | 2 |
| **11.2.4** | 验证所有密码学操作都是常数时间操作，在比较、计算或返回中没有“短路”操作，以避免泄露信息。 | 3 |
| **11.2.5** | 验证所有密码学模块都能安全地处理故障，并且错误处理方式不会产生填充预言机（Padding Oracle）攻击等漏洞。 | 3 |

## V11.3 加密算法

基于 AES 和 CHACHA20 构建的认证加密算法，是现代密码实践的支柱。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **11.3.1** | 验证未使用不安全的分组模式（例如 ECB）和弱填充方案（例如 PKCS#1 v1.5）。 | 1 |
| **11.3.2** | 验证只使用已批准的密码学算法和模式，例如采用 GCM 模式的 AES。 | 1 |
| **11.3.3** | 验证加密数据受到保护，防止未经授权的修改，优先使用已批准的认证加密方法，或将已批准的加密方法与已批准的 MAC 算法组合使用。 | 2 |
| **11.3.4** | 验证 nonce、初始化向量和其他一次性数字不会被用于多个加密密钥和数据元素组合。生成方法必须适合所使用的算法。 | 3 |
| **11.3.5** | 验证任何加密算法和 MAC 算法的组合都以 encrypt-then-MAC 模式运行。 | 3 |

## V11.4 哈希和基于哈希的函数

密码学哈希用于多种密码学协议，例如数字签名、HMAC、密钥派生函数（KDF）、随机位生成和密码存储。密码学系统的安全性取决于其底层哈希函数的强度。本节概述在密码学操作中使用安全哈希函数的要求。

对于密码存储，以及密码学附录，[OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#password-hashing-algorithms) 也会提供有用背景和指导。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **11.4.1** | 验证在通用密码学用例中只使用已批准的哈希函数，包括数字签名、HMAC、KDF 和随机位生成。MD5 等禁止使用的哈希函数不得用于任何密码学目的。 | 1 |
| **11.4.2** | 验证密码使用已批准、计算开销较高的密钥派生函数（也称“密码哈希函数”）存储，并根据当前指导配置参数。参数设置应在安全性和性能之间取得平衡，使暴力破解攻击在所需安全等级下足够困难。 | 2 |
| **11.4.3** | 验证用于数字签名、数据认证或数据完整性的一部分的哈希函数具有抗碰撞性，并具备适当位长。如果需要抗碰撞性，输出长度必须至少为 256 位。如果只需要抵抗第二原像攻击，输出长度必须至少为 128 位。 | 2 |
| **11.4.4** | 验证应用从密码派生秘密密钥时，使用带密钥拉伸参数的已批准密钥派生函数。所用参数必须在安全性和性能之间取得平衡，防止暴力破解攻击危及派生出的密码学密钥。 | 2 |

## V11.5 随机值

密码学安全伪随机数生成（CSPRNG）极难正确实现。通常，系统内高质量熵源如果过度使用会很快耗尽，而随机性较弱的来源可能导致可预测密钥和秘密。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **11.5.1** | 验证所有预期不可猜测的随机数和字符串都必须使用密码学安全伪随机数生成器（CSPRNG）生成，并至少具有 128 位熵。注意，UUID 不满足这一条件。 | 2 |
| **11.5.2** | 验证正在使用的随机数生成机制被设计为即使在高需求下也能安全工作。 | 3 |

## V11.6 公钥密码学

当多个参与方之间无法或不适合共享秘密密钥时，会使用公钥密码学。

作为其中一部分，需要使用已批准的密钥交换机制，例如 Diffie-Hellman 和椭圆曲线 Diffie-Hellman（ECDH），以确保密码学系统能够抵御现代威胁。“安全通信”章节提供了 TLS 要求，因此本节要求适用于除 TLS 之外使用公钥密码学的场景。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **11.6.1** | 验证密钥生成和播种，以及数字签名的生成和验证，只使用已批准的密码学算法和运行模式。密钥生成算法不得生成容易受到已知攻击的不安全密钥，例如易受 Fermat 分解攻击的 RSA 密钥。 | 2 |
| **11.6.2** | 验证密钥交换（例如 Diffie-Hellman）使用已批准的密码学算法，并重点确保密钥交换机制采用安全参数。这可以防止针对密钥建立过程的攻击，避免中间人攻击或密码学机制失效。 | 3 |

## V11.7 使用中数据的密码保护

保护正在处理的数据至关重要。建议使用全内存加密、传输中数据加密，以及确保数据在使用后尽快被加密等技术。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **11.7.1** | 验证使用全内存加密，在敏感数据使用期间保护这些数据，防止未经授权的用户或进程访问。 | 3 |
| **11.7.2** | 验证数据最小化确保处理期间暴露的数据量最少，并确保数据在使用后立即或尽快加密。 | 3 |
