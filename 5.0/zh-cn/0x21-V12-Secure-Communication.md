# V12 安全通信

## 控制目标

本章包含与保护传输中数据所需具体机制相关的要求，既包括最终用户客户端与后端服务之间，也包括内部服务与后端服务之间。

本章倡导的一般概念包括：

* 确保对外通信已加密，理想情况下内部通信也应加密。
* 使用最新指导配置加密机制，包括首选算法和密码套件。
* 通过使用签名证书，确保通信未被未授权方拦截。

除概述一般原则和最佳实践外，ASVS 还在附录 C - 密码学标准中提供了关于密码强度的更深入技术信息。

## V12.1 通用 TLS 安全指导

本节提供关于如何保护 TLS 通信的初始指导。应持续使用最新工具审查 TLS 配置。

虽然使用通配符 TLS 证书本身并不不安全，但如果某个证书部署在所有自有环境中（例如生产、预发布、开发和测试）并被攻破，可能会危及使用该证书的应用安全姿态。应尽可能妥善保护、管理证书，并在不同环境中使用独立 TLS 证书。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **12.1.1** | 验证只启用最新推荐版本的 TLS 协议，例如 TLS 1.2 和 TLS 1.3。TLS 协议的最新版本必须作为首选项。 | 1 |
| **12.1.2** | 验证只启用推荐的密码套件，并将最强密码套件设置为首选。L3 应用必须只支持提供前向保密性的密码套件。 | 2 |
| **12.1.3** | 验证应用在使用 mTLS 客户端证书身份进行认证或授权之前，会验证该证书可信。 | 2 |
| **12.1.4** | 验证已启用并配置适当的证书吊销机制，例如 Online Certificate Status Protocol（OCSP）Stapling。 | 3 |
| **12.1.5** | 验证应用 TLS 设置中启用了 Encrypted Client Hello（ECH），以防止 TLS 握手过程中暴露敏感元数据，例如 Server Name Indication（SNI）。 | 3 |

## V12.2 与外部服务的 HTTPS 通信

确保应用暴露的所有面向外部服务的 HTTP 流量都使用加密方式发送，并使用公开受信任证书。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **12.2.1** | 验证客户端与面向外部的、基于 HTTP 的服务之间的所有连接都使用 TLS，且不会回退到不安全或未加密通信。 | 1 |
| **12.2.2** | 验证面向外部的服务使用公开受信任的 TLS 证书。 | 1 |

## V12.3 通用服务间通信安全

服务器通信（内部和外部）不只是 HTTP。与其他系统之间的入站和出站连接也必须安全，理想情况下应使用 TLS。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **12.3.1** | 验证所有进出应用的入站和出站连接都使用 TLS 等加密协议，包括监控系统、管理工具、远程访问和 SSH、中间件、数据库、大型机、合作伙伴系统或外部 API。服务器不得回退到不安全或未加密协议。 | 2 |
| **12.3.2** | 验证 TLS 客户端在与 TLS 服务器通信前会验证收到的证书。 | 2 |
| **12.3.3** | 验证应用内部基于 HTTP 的服务之间的所有连接都使用 TLS 或其他适当传输加密机制，且不会回退到不安全或未加密通信。 | 2 |
| **12.3.4** | 验证内部服务之间的 TLS 连接使用可信证书。当使用内部生成或自签名证书时，调用方服务必须配置为只信任指定的内部 CA 和自签名证书。 | 2 |
| **12.3.5** | 验证系统内部相互通信的服务（服务间通信）使用强认证，确保每个端点的身份都经过验证。必须采用 TLS 客户端认证等强认证方法，借助公钥基础设施和抗重放机制确认身份。对于微服务架构，可考虑使用服务网格来简化证书管理并增强安全性。 | 3 |
