# V15 安全编码和架构

## 控制目标

许多 ASVS 要求要么与认证、授权等特定安全领域相关，要么与日志、文件处理等特定类型的应用功能相关。

本章提供在设计和开发应用时应考虑的通用安全要求。这些要求不仅关注清晰架构和代码质量，也关注应用安全所必需的特定架构和编码实践。

## V15.1 安全编码和架构文档

要建立安全且具备防御能力的架构，许多要求都依赖清晰的文档，以记录特定安全控制和应用所用组件的实现决策。

本节概述文档要求，包括识别被视为包含“危险功能”或属于“风险组件”的组件。

包含“危险功能”的组件可以是内部开发组件或第三方组件，它执行的操作包括不可信数据反序列化、原始文件或二进制数据解析、动态代码执行，或直接内存操作。这类操作中的漏洞可能带来很高风险，导致应用被攻破，并可能暴露其底层基础设施。

“风险组件”是指开发流程或功能缺少安全控制，或者安全控制实现较差的第三方库（即非内部开发库）。例如维护不佳、不再受支持、已到生命周期末期或曾出现重大漏洞的组件。

本节还强调为修复第三方组件漏洞定义合适时限的重要性。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **15.1.1** | 验证应用文档基于风险定义了存在漏洞的第三方组件版本的修复时限，以及一般库更新时限，以尽量降低这些组件带来的风险。 | 1 |
| **15.1.2** | 验证维护了所有在用第三方库的清单，例如软件物料清单（SBOM），并验证组件来自预先确定、可信且持续维护的仓库。 | 2 |
| **15.1.3** | 验证应用文档识别了耗时或资源密集型功能。文档必须说明如何防止过度使用这些功能而导致可用性下降，以及如何避免生成响应所需时间超过调用方的超时时间。可采用的防御措施包括异步处理、使用队列，以及限制每个用户和整个应用的并行进程数。 | 2 |
| **15.1.4** | 验证应用文档标出被视为“风险组件”的第三方库。 | 3 |
| **15.1.5** | 验证应用文档标出应用中正在使用“危险功能”的部分。 | 3 |

## V15.2 安全架构和依赖

本节包含通过依赖管理处理高风险、过时或不安全依赖和组件的要求。

它还包括使用沙箱、封装、容器化和网络隔离等架构级技术，降低使用“危险操作”或“风险组件”（如上一节定义）的影响，并防止因过度使用资源密集型功能而导致可用性损失。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **15.2.1** | 验证应用只包含未超过已记录更新和修复时限的组件。 | 1 |
| **15.2.2** | 验证应用已根据相关文档化安全决策和策略，实现防护，以避免因耗时或资源密集型功能导致可用性损失。 | 2 |
| **15.2.3** | 验证生产环境只包含应用运行所必需的功能，不暴露测试代码、示例片段和开发功能等额外功能。 | 2 |
| **15.2.4** | 验证第三方组件及其所有传递依赖都来自预期仓库，无论该仓库由内部拥有还是外部来源，并且不存在依赖混淆攻击风险。 | 3 |
| **15.2.5** | 验证应用对文档中标记为包含“危险功能”或使用“风险组件”第三方库的部分实施额外保护。保护措施可以包括沙箱、封装、容器化或网络级隔离等技术，以延缓并阻止已攻破应用某一部分的攻击者横向移动到应用其他位置。 | 3 |

## V15.3 防御式编码

本节覆盖由特定语言中不安全编码模式导致的漏洞类型，包括类型转换混淆、原型污染等。有些漏洞可能并不适用于所有语言，另一些则有语言特定修复方式，或与某种语言或框架处理 HTTP 参数等功能的方式相关。它还考虑未对应用更新进行密码学验证的风险。

本节也考虑使用对象表示数据项，并通过外部 API 接受和返回这些对象所带来的风险。在这种情况下，应用必须确保不应可写的数据字段不会被用户输入修改（批量赋值），并且 API 应选择性返回数据字段。当字段访问取决于用户权限时，应结合“授权”章节中的字段级访问控制要求考虑。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **15.3.1** | 验证应用只返回数据对象中所需的字段子集。例如，不应返回整个数据对象，因为其中某些单独字段不应被用户访问。 | 1 |
| **15.3.2** | 验证当应用后端调用外部 URL 时，除非这是预期功能，否则配置为不跟随重定向。 | 2 |
| **15.3.3** | 验证应用通过限制每个控制器和操作允许处理的字段来防范批量赋值攻击，例如禁止插入或更新本不应由该操作处理的字段值。 | 2 |
| **15.3.4** | 验证所有代理和中间件组件都使用最终用户无法操纵的可信数据字段正确传递用户原始 IP 地址，并且应用和 Web 服务器会将该正确值用于日志和速率限制等安全决策，同时考虑到即使是原始 IP 地址也可能因动态 IP、VPN 或企业防火墙而不可靠。 | 2 |
| **15.3.5** | 验证应用明确确保变量类型正确，并执行严格相等和比较操作。这样做是为了避免应用代码对变量类型作出假设而导致类型转换混淆或类型混淆漏洞。 | 2 |
| **15.3.6** | 验证 JavaScript 代码以防止原型污染的方式编写，例如使用 Set() 或 Map() 而不是对象字面量。 | 2 |
| **15.3.7** | 验证应用具备防御 HTTP 参数污染攻击的措施，尤其是在应用框架不区分请求参数来源（查询字符串、正文参数、Cookie 或头字段）时。 | 2 |

## V15.4 安全并发

并发问题，例如竞态条件、检查时到使用时（TOCTOU）漏洞、死锁、活锁、线程饥饿和不当同步，可能导致不可预测行为和安全风险。本节包含帮助缓解这些风险的多种技术和策略。

| # | 描述 | 级别 |
| :---: | :--- | :---: |
| **15.4.1** | 验证多线程代码中的共享对象（例如缓存、文件，或由多个线程访问的内存对象）通过线程安全类型和锁、信号量等同步机制安全访问，以避免竞态条件和数据损坏。 | 3 |
| **15.4.2** | 验证对资源状态（例如存在性或权限）的检查，以及依赖这些检查的动作，会作为单个原子操作执行，以防止检查时到使用时（TOCTOU）竞态条件。例如，在打开文件前检查文件是否存在，或在授予访问前验证用户访问权限。 | 3 |
| **15.4.3** | 验证一致地使用锁，避免线程因相互等待或无限重试而卡住，并且锁定逻辑保留在负责管理资源的代码中，以确保锁不会被外部类或代码无意或恶意修改。 | 3 |
| **15.4.4** | 验证资源分配策略通过确保公平访问资源来防止线程饥饿，例如利用线程池，让较低优先级线程能够在合理时间内继续执行。 | 3 |
